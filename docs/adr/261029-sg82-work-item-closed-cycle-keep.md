# Work items gain closed, cycle and keep fields (layout 0.3.0)

## Context

A closed work item records `created` and `updated`, but `updated` changes whenever anyone touches the file, so the day an item closed is lost. The only trace is the git commit that moved it into `done/`, and the tool does not depend on git. Grouping closed work by period, folding it into digests, and judging what to keep all need that date, and teams that plan in cycles (sprints, program increments, quarters) need a stable label to group by. Both are cheaper to capture now than to reconstruct later. Compaction itself is a later decision.

## Considered Options

- Derive the close date from git history when needed. Rejected: fragile after squashes and renames, and the tool does not require git.
- Separate fields for each level of a cadence (`year`, `pi`, `sprint`). Rejected: it bakes one organization's cadence into the format, and other teams have one level or four.
- A single opaque `cycle` label the tool does not interpret.
- Counters of how often a record is read, to find valuable notes. Rejected: reads would write to tracked files, and counters conflict between writers. Inbound references from live records are computed on demand instead and need no field.
- A manifest key naming a script that computes the cycle. Rejected: it makes the tool run code from a repository file.

## Decision

Three optional fields on work items, added in layout 0.3.0 (the layout, the four extensions and the spec move together, as in 0.2.0):

- `closed: <YYYY-MM-DD>`: the day the item was closed, in the local day like `updated` (`as_of` wins). The `close` operation sets it for both `done` and `dropped`; it is the only operation that does, and `set` cannot change it. A rule warns when an item in `done/` has none, and reports an error when an open item has one.
- `cycle: <label>`: the cycle the item is planned into, for example `2026-PI3-S4`. It matches `[A-Za-z0-9][A-Za-z0-9._-]{0,63}`, so it is safe in a path or a wikilink. The tool treats it as opaque: it can set, show, list and filter by it, but it does not order labels or know what they mean. The completed cycle is derivable from `closed` once a calendar exists.
- `keep: true`: marks an item as never to be folded or archived. `false` and absence are the same.

Not decided here, and suggested for later: a calendar file in the docs dir that lists periods as `{id, start, end, in}`, generated by the user's own script and read as data; a built-in shortcut of an anchor date, a length and a label pattern for regular cadences; a rule that checks `cycle` against the calendar; compaction of closed work, which skips `keep` items and items with inbound references from live records. The tool will not run a script named by a repository file.

## Consequences

- A MINOR layout change (0.3.0): the work item schema, the check rules, `close`, `set`, `show`, `ls` and the board, the spec and guide, the API schemas and fixtures all change. Existing items stay valid; those already in `done/` get the missing-`closed` warning until someone backfills them (from git history, once).
- Every path that closes an item writes the date. Today that is the `close` operation, which the CLI, the HTTP binding and the workbench all use.
- The format does not assume any team's cadence.
