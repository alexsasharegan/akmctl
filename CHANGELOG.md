# Changelog

## Unreleased

- New command `akmctl split <id> <slug>... [--kind <kind>] [--priority <n>]`: files one `raw` child per slug under a work item, each with the parent's priority unless one is given, prints one `file` commit message per child, and then lists what the parent still needs (its Goal and Next, its claim, `ready`). It edits none of that and creates nothing if a slug is invalid or repeated, or the parent is closed. It is a command-line convenience over `new`, not an API operation. The "Item too big" section of the `akm-track-work` skill now uses it (both copies; run `akmctl skills status`). Affects people and agents who split an oversized item. Glossary term "Split". Work item 261031-ph53.
- `akmctl new` takes `--parent <id>`, `--kind <kind>` and `--priority <n>` for a work item, so a child is filed in one command instead of `new`, `set` and `section`. An unknown parent is `not_found`; the API already took these as `fields`, so only the command line changed. `new --help` lists them. Affects people and agents who split an item. Work item 261031-ph53.
- A parent now shows its progress. `show` and `ls --tree` give a work item with children `progress`: `children_done`, `children_dropped`, `children_total` and the same three for every level below, computed from the `parent` links and never stored; a dropped child is counted apart from a done one. `ls` gains `tree` (`--tree`): children follow their parent, each record has a `depth`, and the text view indents and prints `(2/4 done, 1 dropped)`. `close` of a child now names its `parent`, the `open_siblings` left and `parent_closable`, and the text view says when the parent can be closed. Affects people who split work and clients that read `show`, `ls` or `close` (all additive). API spec sections 4.2, 4.4 and 4.12, schemas, fixtures `show-3`, `ls-7` and `close-2` to `close-8` in both copies, glossary term "Progress counts". Work item 261031-72bd.
- The commit message of a `set` that blocks a work item now names every blocker: `261026-m1n2(block): blocked on a, b, c`. It was the first only. Past 60 characters it stops and ends `and N more`; the first blocker is always named. Affects clients that read `commit.detail` of a `block` step and anyone who commits with the message as given. API spec section 1 (the `commit` member). Work item 261101-3erc.
- The workbench gains two opt-in animations, from the 4n0v spike: a `tetris` lane-move theme (a stepped drop beside the default `quiet` slide) and a confetti cannon when an item moves to `done`. Both are off until the reader chooses them with the command palette ("Animations: ..."), the choice is kept in the browser (`akm-anim`), and nothing plays under `prefers-reduced-motion`. Affects people who watch the board. Work item 261101-4n0v; follow-ups 261107-49ta (settings control), 261107-qsd4 (more themes), 261107-7v9y (fizzle and streaks).
- The workbench capture modal is reworked: the heading comes first with a muted "New work item" line below it and "Raw" set in Monaspace Radon, the dialog is wider (720px) with the parent search on its own row, and the submit button has a style of its own with a visible focus ring in both themes. It gains an optional Cycle field next to Priority, checked against the pattern `set` uses. To file straight into a cycle, the `new` operation (`POST /records`, `akmctl new`) now accepts `cycle` in `fields` for a work item (API spec section 4, `new`); other values of the field are refused as before. Affects people who capture from the workbench and clients that call `new`. Work item 261029-aezq.
- New command and operation `akmctl bases` (`POST /bases`): writes an Obsidian Bases file, `docs/akm.base` by default, with table, cards and Kanban views of the work items (open by parent, ready and active, blocked, stale, recently closed, by status, parent and cycle) and a table of the ADRs. It is written once and never overwritten (a file that exists is `refused`, `details.reason: "exists"`); folder filters start at the nearest `.obsidian` folder above the repository and use the manifest's `work_dir`, `adr_dir` and `stale_days`. Adds the operation to the API spec (section 4.25), its schema, four fixture cases and a fixture repository (`obsidian`), a skill reference `bases.md`, and the glossary term. Affects people who keep records in an Obsidian vault and anyone who binds the API. The tool cannot open Obsidian, so the maintainer checks that every view renders. Work item 261029-kb88.

- The workbench record drawer shows a record's fields as a typed table (each value labelled text, date, number, flag, list, link or id; lists one item per line) and edits the fields of an open work item in place: summary, kind, priority, parent, blocked_by, cycle and keep, each through `set` with the record's etag. A locked field says why (changing kind or parent on an active item warns), a write refused by the API shows its message beside the field, and a record that changed since it was opened shows a conflict and writes nothing. A closed item stays read-only except `keep`. Affects people using the workbench. Work item 261028-esyt.

- The workbench capture modal's parent field is now a searchable list: type to search open work items by id, title or summary, with what matched marked, each row showing the id, title, status and summary; arrows and Enter choose, Escape closes only the list. It replaces the browser's plain suggestion list. Affects people using the workbench; the picker is shared with the drawer editor (261028-esyt) to come, and its multi-select form for `blocked_by` (chosen items as removable chips) is ready for it. Work item 261029-bdt9.

- The workbench capture modal has a custom select for the kind (open with Enter, Space or the arrows, Escape closes it, type a letter to jump) and a summary text area that wraps and counts: the counter warns from 144 of 160 characters and says "limit reached" at 160, in words as well as colour. A pasted line break becomes a space, and Enter in the summary captures as before. Affects people using the workbench; the controls are shared with the drawer editor (261028-esyt) to come. Work item 261029-kb33.

- New command `akmctl agents`: prints the `AGENTS.md` that `init` would write for this repository, filled from its manifest (records folder, wikilinks) and read-only, so a repository whose `AGENTS.md` predates a template change can compare the two and keep the lines it judges. Affects: anyone upgrading an existing repository; nothing is written. Work item 261101-abw2.

- The workbench replays moves made while you were away in the order they were committed, naming who made each (the `Assisted-by` value, else the commit author) and showing the path an item took, not only where it ended. It reads the `history` operation, so it needs a git work tree with `git_commits` on; otherwise it falls back to the old snapshot comparison (moves by id, "Outside"). A burst of more than ten moves, or reduced motion, still shows one summary toast and now also lists every move in a panel; a page load lists what was committed since the last visit. Limits: a round trip with no net change is not shown, and a move committed after it was seen live is listed again on the next load (work item 261101-w0mz, ADR 261106-60xv).

- New `history` operation, `akmctl history [--range <range>] [--limit <n>] [--item <id>]` and `GET /history`: the AKM step commits of a range as moves, oldest first, each with the item, step, author, time, the item's status before and after and the other trailers (for example `Assisted-by`). Without a git work tree, or with `git_commits` off, it answers `available: false` with a reason instead of failing. Read-only; the workbench replay of missed moves builds on it. API 1.x: a new operation, schema `history.json` and a reference in the `akm` skill (so `skills update` adds `references/history.md`) (work item 261106-sdnr, ADR 261106-60xv).

- The guide has an Upgrading section (`docs/spec/akm-guide.md`, section 8): for the binary, the skills, `AGENTS.md` and the layout, what changes, the command to run and what it leaves alone. Documentation only; no command, API or rule changes (work item 261101-wghm).

- `close` (and `section` with empty text) no longer leaves two blank lines after an emptied `## Next` when the heading is followed by a blank line, so a closed record passes `npm run format:check` without a formatting-only commit; a section that ends the file keeps just its heading. Records written without blank lines after headings are unchanged. API 1.x: the closed file differs by blank lines only (work item 261101-w82x).

- `commits` has a new rule, CM5: a step commit whose `AKM-` trailers are not in the last paragraph of the message is reported, because git reads trailers only from there (an agent that passes the message as one `git commit -m` per line, or leaves a blank line between the `AKM-` trailers and an `Assisted-by` or `Co-Authored-By` trailer, loses them). Pass the whole message to one `git commit -F -`. The printed block, the `akm-commit` skill and the command references say so. A run over older history reports every commit made that way; use `--range` for the branch. API 1.x: a client of `commits` may now see rule `CM5` (work item 261101-ft79).

- A parameter that must match a pattern now says what the value looks like when it does not: `at: "09:46" has the wrong form; expected YYYY-MM-DD HH:MM (or YYYY-MM-DDTHH:MM), with an optional offset such as +02:00`. Covers ids, dates, `as_of`, `at`, versions, cycles and etags. API 1.x: the `invalid_request` message is longer; the code, the `param` and the rule are unchanged (work item 261101-y3ch).

- Agents attribute their work with `Assisted-by: <agent and model>` on commits and an `Assisted by <agent>` line on pull requests, in place of `Co-Authored-By`; the rule is in this repository's `AGENTS.md`. Affects agents working here and the trial protocol row R13; no command, API or rule of the tool changes (work item 261106-jkj9, ADR 261106-zvpm, which supersedes 261101-z0mt).

- The `AGENTS.md` template that `init` writes, and the `akm-track-work` and `claim` skill references, now tell an agent to claim with a name unique to its session (`--as <agent>-<model>`, not a bare `claude`) and to treat an `unknown command` as a possible stale binary (`akmctl version`, `akmctl skills update`) before filing a tool bug. The `claim` example in `akmctl help` uses such a name. The `AGENTS.md` template changed: run `akmctl agents` and compare it with your file. Existing repositories get the new wording with `akmctl skills update` for the skills; their `AGENTS.md` is never rewritten. No change to any command or the API (work item 261101-qr8x).

- The workbench project filter now groups by `parent`: a project is a parent with children, and choosing one shows it and everything beneath it. It no longer reads the old `project` frontmatter field, which came from the pkm vault and is ignored by `check`; items that still carry it just lose the filter. The word "umbrella" is struck from the glossary and skills in favour of "project". Work item 261101-kngg.

- Rule S2 accepts YAML block scalars (`description: >`, `|`, with `-`, `+` and indentation indicators) in a skill's `SKILL.md` frontmatter, and checks the folded value of `name` and `description` as YAML reads it. Before, a skill with a folded description failed S2 with `block scalars are not supported` until someone unfolded it by hand. A record's frontmatter still rejects block scalars; every other line of a skill's block is read as before. No API change: the finding is the same rule, no longer reported for this input (work item 261029-wpak).

- New `scripts/install.sh`, a one-command install for macOS and Linux: `curl -fsSL https://raw.githubusercontent.com/alexsasharegan/akmctl/main/scripts/install.sh | sh` downloads the latest release archive for the machine, verifies it against `SHA256SUMS` and installs `akmctl` into `~/.local/bin` (`AKMCTL_VERSION`, `AKMCTL_INSTALL_DIR`). The README install section leads with it. No change to the tool or the API (work item 261101-wgf6).

- `close` empties a non-empty `## Next` (the heading stays), because a closed item has no next step; a plan left there only misleads. `commits` has a new rule, CM4: a commit with no AKM step that changes the `status` or `claimed_by` of an open work item in place is reported instead of skipped; use the message the command printed. A run without `--range` may now report old hand-made status edits. API 1.x: a client that read `## Next` of an item it just closed gets it empty. Fixtures `close-2`..`6` and `close-8` in both copies (work item 261101-avg8, ADR 261101-8cd9).

- `akmctl log` warns on stderr when the shell passed several words instead of one quoted message, showing the line it joined (`joined 3 words into one Log line: "..."`), and still writes it. An unquoted `;`, `&`, `|` or `>` cuts a message short and runs the rest as another command; the warning makes that visible. CLI binding only: stdout, the exit code and the API are unchanged. The `log` reference in the skills now shows a quoted message (work item 261101-jgdy, ADR 261101-5k3t).

- `claim` is refused (`reason: "rule"`, `rule: "WK6"`) when the item's `## Next` is empty, instead of making it `active` and leaving `check` to fail. Write the section first (`akmctl section <id> Next --text "..."`), then claim. API 1.x: a client that claimed a `ready` item with no `Next` now gets this error. Fixture `claim-3` with a new repository `claimsnonext`, and `claim-1` now claims an item that has a `Next`, in both copies (work item 261101-p2m8, ADR 261101-09yd).

- `akmctl <command> --help` (or `-h`) and `akmctl help <command>` print the command's flags and one example and exit 0, instead of failing with `unknown parameter "help"` (work item 261101-m3pv). A test fails for any command without an example.
- Closed work items are read-only (ADR 261101-dxcn, work item 261101-3vwz): `set` and `section` on a `done` or `dropped` item are `refused` (`reason: "closed"`) unless the call carries `correction` (`--correction "<why>"`), which writes `corrected <fields>: <why>` to the Log in the same write. Only `title`, `summary` and prose sections can be corrected (`closed_field` otherwise, and always for the Log); `keep` stays editable with no reason. Before this, `set` changed any field of a closed item. API 1.x, additive for `correction`; a `set` that edited a closed item without it is now refused.
- New operation `remove` (API 1.x, additive): `akmctl remove <id> <n> --reason <text> --confirm` deletes one unchecked box of a checklist and appends `removed "<box text>": <reason>` to the Log in the same write. It loses history, since the tool does not track git, so without `--confirm` it is `refused` (`reason: "confirm_required"`) with a message that says so and recommends committing first; a `--dry-run` needs none. Ticked boxes are refused (`ticked_box`). The `close` refusal for an unchecked Goal names it. Work item 261101-zq7c.
- `close <id> done` is refused (`reason: "unchecked_goal"`) while the item's `## Goal` has an empty box, naming each box with its line and, when `tick` can address it, its number. `dropped` is not checked; there is no override flag: tick the box, `remove` it, change the Goal with `section`, or drop the item. `tick` takes `evidence` (`--evidence`), which appends `ticked "<box text>": <evidence>` to the Log in the same write. A repository's open items with empty boxes now need them ticked before `close done`. Fixtures `close-9` and `tick-6` in both copies; fixture items `261020-a2b3` have a ticked Goal so that the other close cases still close (work item 261031-zek2).

- Ordered-list tasks are checklist items: `1. [ ] step` and `2) [x] step` are read as tasks, count with the bullet boxes in one run (`tick <id> <n>` keeps a single stable index), and tick by one byte like the others. An ordered line is claimed only when CommonMark reads it as a list item (after a blank line, starting at 1, or the next item of the list above); the oracle battery and all three fuzz targets agree. Nested markers (`1. 1. [ ]`), a box without text and more than four spaces after the marker stay local refusals. This supersedes the interim decision in 261101-xher. Fixture `tick-5` with a new repository `orderedgoal`; `section-7` and `check-8` now use a tab after a list marker as their local construct (work item 261101-wder).

- The scanner reads two HTML shapes it used to refuse: a comment that ends on its own line (`<!-- c -->`) and a line that starts with an inline tag and has text after it (`<b>bold</b> text`, `</b> tail`). Neither can open an HTML block, so neither can swallow a heading; the oracle battery and both fuzz targets agree. Other HTML lines (`<div>`, `<br>`, a tag alone on its line, a comment that spans lines) stay structural refusals. An ordered-list task (`1. [ ] x`) stays a local refusal, with the reason in the code (work items 261101-v65x and 261101-xher).

- A Log line carries the writer's local time and offset: `log`, `claim` and `release` write `- 2026-11-01 16:02-07:00: text`. `log` takes `at` (`--at`) for when the thing happened; the line ends `(at 11:05-07:00)`, and an `at` after the write is `invalid_request`. A date-only `as_of` still writes a date-only line; an `as_of` with a time writes `+00:00`. Date-only lines stay valid and are not rewritten; `Tree.LogEntries` reads both and `Entry` gains `Time` and `Offset`. The AKM spec template, the glossary (new Time conventions), the `akm` skills, the `log` schema and fixtures `claim-1`, `log-3`..`5` in both copies change (work item 261101-vy77, ADR 261101-gw7b).

- New operations `tick` and `log` (API 1.x, additive). `akmctl tick <id> <n> [--undo]` sets or clears one checkbox of the Goal by position and changes one byte of the file; `akmctl log <id> <text>` adds a dated Log line. Both set `updated` in the same write, take `dry_run`, and take `section_etag` (the section's hash, returned in every response) so a write applies when its section is unchanged even if the rest of the file moved. HTTP: `PUT /records/{id}/sections/{name}/items/{n}` and `POST /records/{id}/log`. A closed record, a missing section or item, a stale etag, and a body with an unsupported construct are refused as for `section`. Fixtures `tick-1`..`4` and `log-1`..`2` in both copies; `akm` skill references `tick` and `log` (work item 261101-ga4s, ADR 261101-tr8e).

- `section`, `close --outcome` and the Log line of `claim` and `release` write through the section tree. The line scan `SetSection` is gone. Bytes outside the edited section are never changed. A body with a structural construct, or a local one in the section being written, is `refused` with `details.reason: "unsupported_markdown"`, the construct and the file's line, and nothing is written. Clearing a section that is already empty no longer adds a blank line. Fixture `section-7` in both copies (work item 261101-q72k, ADR 261101-tr8e).

- `check` warns (rule B1) about a record body that `akmctl` does not read: it names the construct and line, and says whether no write is safe (structural) or only writes to that section are refused (local). Blockquotes are read as opaque text and are not reported. In the maintainer's vault, 2 of 435 work-item sections hold a local construct, where 18 of 138 files used to be refused whole (work item 261101-4j86, ADR 261101-tr8e). Fixture `check-8` in both copies.

- `close` repairs the relative Markdown links its move into `done/` breaks: the item's own links are re-based and the inline links to it in other records, the roadmap, AGENTS.md and the docs are rewritten. The response has `links_rewritten` and, for a file it could not write, `link_errors`; `commit.paths` lists every file written. Fixture `close-8` in both copies; new package `internal/mdlinks`, which `check` rule L1 now uses too (work item 261031-wjs3).

- A code fence now closes only on the same character and at least as long a run, in `section` and every other heading search, as in the body scanner (work item 261031-2j14).

## 0.3.3 - 2026-10-31

- `close <parent> dropped` is refused (`open_children`, WK8) while a child is open, as for `done`, and `check` applies WK8 to a `dropped` parent and to open descendants below a settled child. Before, the spec's rule for dropping a parent was not enforced and the open child was left under a closed parent. A repository that already has such a parent now fails `check`: drop or re-parent the open children (work item 261031-6c5n).

- `new` is refused (WK18) when its `fields` give a `parent` and a `blocked_by` that close a dependency cycle, such as a child blocked by its own parent. This was reachable through the API and the workbench capture form. Fixtures `new-1` and `close-7` in both copies (work item 261031-btdz).

- `check` warns (rule WK19) when an item lists one of its own descendants in `blocked_by`: a parent already waits for its children, so the entry is redundant. It is a warning and not a cycle. Fixture `check-7` in both copies (work item 261031-pbws).

- `check` reports a dependency cycle (rule WK18): items that wait for each other through `blocked_by` entries and parent-to-child links, for example two items blocked on each other, a longer loop, or a child blocked by its own parent or grandparent. One finding per cycle, naming the items in order. A loop in the `parent` links alone is now one WK4 finding per loop, at its lowest id, instead of one per item that leads into it. `set` refuses a `blocked_by` entry or a `parent` that would close such a cycle (WK18). A parent that lists its own child in `blocked_by` is redundant, not a cycle, and is accepted. New package `internal/depgraph` (Tarjan's algorithm, O(items + edges)); fixtures `check-6` and `set-11` in both copies (work item 261031-z50q).

- `set` and `new` refuse a `parent` that would close a loop at any depth (WK4, with the chain in the message) or that would put an open item under a `done` or `dropped` parent (WK8). Before, both were accepted and left the repository failing `check`. A violation that is already present does not block an unrelated change. Two fixture cases (`set-9`, `set-10`) in both copies (work item 261031-wy32).

- Specification only: `closable`, `complete`, `settled`, derived `blocked` and the dependency graph (the `blocked_by` entries plus parent-to-child links) are defined, WK8 is restated recursively, and rule WK18 (the dependency graph has no cycle) is added, with the requirement that `set` and `new` refuse a `parent` or `blocked_by` change that adds a WK4, WK8 or WK18 violation. The tool enforces them in work items 261031-wy32 and 261031-z50q; its `check` does not report WK18 until then (work item 261031-xprq).

- `--repo <dir>` naming a folder that has no manifest while a folder above it does is now an error that names the ancestor, for every command but `migrate` and `version`. Before, the tool read that folder as an empty repository with default folders and gave wrong answers without a warning (`commits` reported a false CM3 on correct commits). `--repo` still never climbs: it is the root as given. The same check applies to `akmctl ui --repo` (work item 261030-8aph).

- `find` takes `name` as well as `id`: the target of a wikilink (`Project Notes`, or `Projects/Project Notes`) resolves to the one Markdown file with that name under the repository root, ignoring case and hidden folders, with `not_found` and `ambiguous` as for an id. `akmctl find --name <note>`, `GET /find?name=`; `find.json`, the API spec (4.8), three fixture cases and the `akm` reference are updated. `ui`: wikilinks in the drawer's fields, alone or in a list, are links. They open the note in Obsidian, show the alias, offer a "here" link when the note is a record, and read as unresolved (not clickable) when no note has the name (work item 261029-ctzc).

- `ui`: a card shows a complete border on all four sides when idle or hovered. The left edge was `3px solid transparent`, so only the other three sides drew a line (work item 261029-rmrk).

- `ui`: a project filter in the header narrows the board, the tables and the palette to one project, from the extra frontmatter field `project` (a wikilink; the link target is matched, an alias is ignored). The select shows counts per project and a no-project choice, and is hidden when no work item has the field. The choice is in the URL (`#/board?project=Project%20Notes`, `~` for no project) and is remembered per repository; the palette has a "Show all projects" action. It filters on the client, so the API is unchanged (work item 261029-30my).

- `ui`: the "Recently closed" table no longer flashes when the records reload (`r`). The list is kept across reloads, drawn again at once, and redrawn only if it changed (work item 261029-57jq).

- `ui`: a card shows who holds a claim and for how long (`held by claude, 2 days`). The snapshot now reads `claimed_by` and `claimed_at`; a record with no claim shows nothing (work item 261029-8948).

- `akmctl skills [status|install|update]` is new (ADR 261030-h6t7, accepted): it reports, installs and updates the skills the tool manages, in a repository `init` did not make. Each managed skill folder carries a marker `.akm-skill.json` (tool version and file hashes), so `update` can tell an older shipped copy from an edit; an edited skill is left unless `confirm_edited`, and the retired `akm-work-items` folder is removed by `update` (an unmarked one needs `confirm_edited`). `init` and `config git-commits` write the same markers through the same code. The API spec (section 4.20), the schema `skills.json`, `GET`/`POST /skills`, the `init` and `config` fixtures, the `akm` skill reference `skills.md` and the glossary are updated. Not committed by the tool.

- The skills tell an agent to commit one step at a time with the `commit.message` the tool returns, as given, without needing the optional `akm-commit` skill (work item 261030-0yyn; found when a vault agent ignored the printed message). `akm-track-work` no longer says to commit a whole task together. `skills` adds `notes`, which says when `akm-commit` is not installed and how to turn it on.

- The skill `akm-work-items` is renamed `akm-track-work`, so every skill is a verb and an object (`akm-record-decision`, `akm-track-work`, `akm-commit`) and the router is `akm`; the glossary has the grammar (ADR 261030-wsqb, proposed). `init` writes the new name. A repository made by an earlier `init` keeps the old folder, which still works; the skills installer (work item 261030-8d8t) will retire it.
- The migration log is renamed `.migrate-log` to `.akm-migrate-log` (ADR 261030-1wj5, accepted): files the tool keeps for itself carry the `.akm` prefix, and the files a person recognises (`.layout`, records) do not. A migration that finds the old file renames it first, so its history is kept. The layout version is unchanged; the next layout change records the new name.

- Writes are durable: every record, index and manifest write flushes the temporary file before the rename and the folder after it. Before, a power loss between the rename and the data reaching the disk could leave a short or empty record. The API spec (section 7) says so.

- `new`, `claim`, `release`, `close` and a `set` that changes a work item's `status` return a `commit` object (`step`, `item`, `detail`, `paths`, `message`): the subject `<id>(<step>): <detail>` and the trailers `AKM-Step` and `AKM-Item`, for the caller to commit with. The tool still never stages or commits (ADR 261030-tbkh, proposed). The CLI prints the message and the paths to stage. The API spec, schemas, fixtures (new case `set-8`) and the `akm-commit` skill are updated; `akmctl commits [--range <revs>] [--limit <n>]` is new: it reads `git log` and checks each commit that claims to be an AKM step. CM1 the subject, CM2 the two trailers, CM3 the diff (a `close` moves the file into `done/`, a `claim` leaves it active and claimed, and so on). Read-only, exit 1 when a commit fails; `GET /commits` over HTTP; schema `commits.json`; no fixture cases, since a fixture directory cannot hold a git history (tested against repositories the tests build with `git`).

- `close` returns `dependents`: the open work items (`raw`, `ready`, `active`, `blocked`) whose `blocked_by` names the closed item, for `done` and `dropped` and in a dry run. It only reports and never refuses; the CLI lists them after the move, and a close with none is unchanged. The API spec (section 4.12), `close.json`, the `close` fixtures and the `akm-work-items` and `akm` skills are updated.
